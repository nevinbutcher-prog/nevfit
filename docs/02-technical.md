## Startup recovery

The authenticated program-hydration effect must start a fresh authority read on
each setup and ignore results after its own cleanup. An in-flight UID ref is not
evidence that hydration completed: Strict Mode's setup/cleanup/setup sequence
discarded the original read and skipped its replacement in 070, leaving
`trainingRuntime.mode` permanently loading even after the server responded.

`startupDiagnostics.js` names the authority marker, v2 inventories/stage/recheck
and legacy-program reads, logs start/completion/failure with duration and code
(no account IDs, snapshots or raw SDK messages), and bounds startup reads to 20
seconds. A separate deadline covers all App loading gates, including exercise
notes ownership. Failures render the unresolved operation/code with Reload and
Sign out actions; no fallback selects an unverified training authority. The
obsolete `_smokeTest` query and its caller are removed, since that top-level
collection is denied by the rules and was unrelated to startup hydration.
Normal runtime reads/writes and data-transition confirmation gates are unchanged.

## Active-workout recovery

`workoutRecovery.js` supplies a single presentation decision for the workout
body, fixed timer/footer and normal navigation. A truthy session alone cannot
enter full-screen workout mode. Legacy missing program/workout/day references,
malformed sessions, empty planned sessions and model mismatches enter recovery.
Returning to Dashboard retains the snapshot; a visible reminder links back to
recovery. Starting another workout cannot silently overwrite a recovery session.
An empty Quick Workout remains valid and supports Add Exercise; complete v2 saved
snapshots need neither a current template/program nor an assigned schedule day.

`WorkoutRecovery.jsx` always offers Return to Dashboard and, for stored-session
problems, explicitly confirmed Discard Workout. The latter drains pending active
writes, clears only the scoped active-workout document, then clears that session's
cache/state. A failed cloud clear leaves the session/recovery available, with a
retry message and Dashboard access. Completed history/templates are not changed.
Recovery stops the ephemeral rest timer; disabled Skip is never an exit control.

Active reads are server-only. A missing document may retain a valid same-UID
device snapshot for display, but does not upload it; a recreated UID cannot read
the prior UID's cache. Invalid raw source data stays untouched for explicit
recovery. Hydration captures a baseline and does not trigger autosave until an
actual edit/discard; incomplete/recovery state cannot overwrite cloud data.
The active/session and schedule effects each restart safely after Strict Mode
cleanup, so cancelled reads cannot drop the only valid restoration result.
No Auth account deletion, data migration, storage reset or rule change is part of
this fix. Fresh/Incognito sign-in can still see account-owned cloud snapshots;
the agent did not inspect the affected account to identify its specific orphan.

## AI Transport Foundation

Firebase Functions provides the sole browser-accessible AI boundary. The
callable `aiGenerate` function requires Firebase Authentication and never
trusts a client-supplied user ID. It accepts only a bounded
provider-neutral `{ messages }` request; callers cannot select a provider,
model, output budget, headers, tools, or routing settings.

The production callable runs as a second-generation Node.js 22 function in
`us-central1`. Its Functions package entry point is `functions/src/index.js`.

`functions/src/ai/aiService.js` owns validation and the provider-neutral
service contract. `functions/src/ai/providers/openRouterProvider.js` is the
current OpenRouter adapter and is the only module that knows the OpenRouter
endpoint, headers, and response layout. The server config in `aiConfig.js`
owns the provider, explicit default model, maximum output tokens, and finite
upstream timeout. It performs one request only: there are no automatic retries.

`OPENROUTER_API_KEY` is a Firebase Functions secret bound to the callable
function, never a Vite environment value. Configure it outside source control
with `firebase functions:secrets:set OPENROUTER_API_KEY`. The secret must not
be placed in browser code, Firestore, local storage, logs, or committed env
files.

Responses normalize to text, model, and nullable token usage. Errors normalize
to stable `ai_*` codes and safe messages. Development diagnostics record only
provider/model, result/error code, duration, usage, and whether authenticated
context was present--never prompts, outputs, tokens, emails, or health/training
data. AI responses are transient: this foundation reads or writes no program,
routine, workout, planning, health, or Firestore domain data.

## Catalogue-grounded Rob Program Generation

Whole-program generation prepares a bounded browser-side selection from the existing WGER pool, filtered by confirmed equipment and explicit supplied exclusions. The browser submits only catalogue IDs and a version; Firebase independently maps those IDs through its reviewed server-owned WGER catalogue before creating the AI prompt. Client names, equipment, and eligibility claims are ignored. AI output must use only those exact IDs, and fabricated, stale, malformed, or out-of-catalogue IDs are rejected before a transient executable proposal is materialised.

Catalogue records are capped at 32, carry provider identity, display name, equipment, and muscle metadata, and are deduplicated by display name. The eligibility interface accepts an equipment context and explicit exclusions, ready for a future My Gym adapter without persistence or facility-profile implementation. Successful catalogue-grounded candidates populate trusted resolution entries directly and bypass mandatory name matching. The legacy resolver remains for old free-text candidates and voluntary manual replacements. A conservative deterministic quality assessment reports, but does not reject, clearly underfilled 45-, 60-, and 75-minute sessions.

## Isolated Rob Blueprint Fulfilment

`functions/src/rob/robBlueprintFulfilment.js` is the Card 5, server-side foundation between a validated weekly blueprint and the existing strict program candidate parser. It accepts the confirmed requirements plus a version-matched authorised catalogue ID snapshot. Server catalogue records remain the only exercise identity and metadata source; browser display metadata is ignored.

The engine shares `eligibleRobCatalogueEntry()` with catalogue authorisation, so exclusions, incomplete equipment metadata, and confirmed equipment capabilities have one eligibility interpretation. `createServerAuthorisedRobCatalogue()` is the future Firebase integration entry point: it derives eligible IDs and exclusions from confirmed requirements and server-owned state, rather than a browser catalogue or browser exclusion claim. Each blueprint slot is matched exactly against trusted planning-taxonomy primary muscle, movement pattern, role, and, when declared, a narrow selection intent. The bounded intents distinguish biceps versus triceps isolation, knee flexion versus extension, and lateral/rear/anterior-delt work; omitted or unknown intent remains explicit rather than inferred as interchangeable. Deterministic ranking prefers conventional, confident, low-setup matches and modestly favours complementary choices over repeated identities, without prohibiting legitimate repetitions. It preserves declared slot order, sets, repetitions, and rest; an unmatched slot returns a structured diagnostic rather than substituting another movement.

Successful selections are revalidated by `parseProgramCandidate()` and assessed with the advisory-only quality scorecard. This module has no callable export, provider request, UI, Firestore, or persistence dependency until a later reviewed integration card.

## Structured Rob Reviews

The authenticated `robReview` callable accepts only a deterministic
`routine_review` or `program_review` context. Routine reviews require exactly
one target routine; program reviews use all active routines. The browser sends
no free-form review prompt, provider/model setting, or mutation proposal.

The function asks the provider for one JSON object, accepts direct JSON or one
JSON code fence, and validates a bounded version-1 result before returning it.
Malformed output is rejected as retryable `ai_invalid_response`; raw provider
text is never rendered. Returned targets are derived from the validated context
and optional routine/exercise references are filtered to IDs present there.

Reviews are transient and read-only. The program editor can review its current
in-memory draft without saving it, then presents bounded strengths, concerns,
suggested changes, and limitations. Reviews do not call proposal or persistence
paths and make no claims about recovery, pain, readiness, clinical safety, or
other facts absent from context.

The editor contains only contextual review actions. They switch the shared Rob
panel into routine- or program-review mode and retain a transient builder return
target, so review output never competes with editable routine fields.

### Exercise Resolution

`src/services/exerciseResolution.js` is the reusable deterministic boundary
between an AI exercise description and a trusted provider-backed exercise ID.
It first applies normalized exact matching across the provider display name,
original name, and provider-supplied aliases, plus bounded Fitbot-owned
terminology aliases for unambiguous abbreviations and spelling variants (such
as `RDL`, `SLDL`, pull-down, and skullcrusher). It then uses conservative token
scoring for ordering and wording differences. High-confidence similarity will
not auto-match when a candidate adds or changes a material movement or pressing
variant term (for example curl-and-press, row, squat, flat, or incline). It
never accepts an AI-supplied ID. Weak matches are unresolved; multiple plausible
provider results enter a
transient `needs_resolution` state. The October 2026 audit found WGER returns
920 English records, below Fitbot's 1,500-record pool cap, so no additional
provider is warranted on catalogue-coverage evidence alone. Persistent personal
mappings remain deferred: a confirmed substitution is not necessarily a shared
synonym and must not become an automatic match without an explicit future
user-controlled mapping model.

A captured 16-exercise production-QA fixture records real WGER identities and
metadata in `test/robExerciseMatchingQa.test.js`. It improved the observed baseline from
7 automatic matches to 10 safe automatic matches; five safety-sensitive cases
remain ambiguous (general cable fly, seated shoulder press, weighted Russian
twist, leg press emphasis, and Hackenschmitt calf raise), and treadmill sprints
remain unresolved because ordinary treadmill running does not establish sprint
intensity. The fixture has zero known unsafe automatic matches. Provider
metadata may supply missing equipment wording when it agrees with the request,
but missing or conflicting equipment blocks automatic selection. WGER records
with distinct IDs are no longer semantically deduplicated before resolution, so
identically named records remain an explicit ambiguity.

The user selects one displayed provider result, after which Fitbot reruns normal
proposal validation without making another AI request. No program draft is
mutated during resolution.

When resolution pauses, Fitbot also retains a canonical generation baseline of
the draft on which Rob produced the candidate. Continuing resolution first
compares the latest draft with that baseline: routine changes invalidate a
routine-modification candidate, while any program change invalidates a
routine-creation candidate. A cached candidate is never rebased onto newer
draft state. This check complements, rather than replaces, the normal
preview and approval-time freshness checks.
For routine proposals, the browser supplies only the completed review's bounded
summary, concerns, and suggested changes, including their bounded routine and
routine-exercise references. `robProposal` validates that review shape and
rechecks every reference against the supplied routine context before sending it
separately from that context; stale references are discarded. It instructs the provider
to make only changes supported by those findings. Every candidate operation has
an explicit allowlist of fields before the client resolves exercises and applies
the mandatory routine-proposal validation gate.

`src/services/rob/robProposalApproval.js` is a pure approval boundary. When a

the relevant routine (or program for a create proposal), including routine
name, exercise order and IDs, prescriptions, display names, notes, and
supersets. Approval reads the latest draft through `programDraftsRef`, compares
that baseline, reruns `validateRoutineProposal`, then calls
`applyRoutineProposal` with the newly normalized proposal. A structurally valid
proposal is still blocked if the target draft changed after it was prepared.

Rejecting, stale detection, previewing, and approval itself perform no
persistence. A successful application atomically replaces only the matching
entry in `programDrafts`; it clears the transient proposal and returns the user
to the normal builder, where Save Program remains the only local/cloud commit.
Neither Rob nor this workflow can modify workouts, history, planning, health,
or any persisted data directly.

## Workout History Model

Completed workouts are append-only historical snapshots stored at:

```text
users/{uid}/completedWorkouts/{workoutId}
```

`nevfit_completed_workouts` remains a local cache.

Previous performance is derived from completed workout history globally by
stable `exerciseId`, not by routine, schedule slot, day, or program. It uses
the most recent matching completed exercise with meaningful logged effort, not
active or blank sessions. Routine-level `displayNameOverride` values do not
change that history identity.

Blank workout sessions are non-destructive:

- A session is blank when no set contains meaningful reps or weight.
- Blank sessions are not saved as completed workouts.
- Closing a blank session clears the active workout and leaves completed history unchanged.
- Previous performance lookup ignores blank legacy completed records.

## Program And Routine Model

Program definitions are user-editable and persist separately from workout
history. Workout sessions snapshot the assigned routine at workout start.

The Starter Program is migrated from default routine data. Newly created
programs should start empty and routines are added explicitly through the
program editor.

Routine exercises store a stable `exerciseId` that points to the selected wger
exercise. They can also store an optional `displayNameOverride`, allowing a
base wger movement to be named as a practical routine variant such as
`DB Reverse Lunge`.

Routine exercises also normalize a lightweight `supersetGroupId` field:

```js
{
  routineExerciseId,
  exerciseId,
  sets,
  repRange,
  restSeconds,
  displayNameOverride,
  note,
  supersetGroupId,
}
```

`routineExerciseId` is the stable identity of a particular row inside a
routine. It is separate from provider-backed `exerciseId`, so two instances of
the same movement can be targeted independently. New rows receive a generated
`ri-*` ID. Legacy rows receive a deterministic `ri-{routineId}-{position}` ID
during normalization; the ID is then retained through edits, reordering, and
persistence. Duplicating a routine generates fresh row IDs for the copy.

Missing values normalize to `null`. Older `groupId` values are migrated into
`supersetGroupId` during routine normalization for local backwards
compatibility, but new routine data writes `supersetGroupId`.

Supersets are stored as shared group IDs, not one-way exercise links. Pairing
two ungrouped exercises creates a new `ss-*` group ID. Pairing with an exercise
already in a group joins that group. Removing a pairing or deleting an exercise
cleans up orphaned groups so a remaining single exercise has
`supersetGroupId: null`.

The routine editor exposes pairing through a focused partner selector keyed by
routine-row index, so duplicate base exercise IDs remain independently
targetable. Changing a pairing first removes the edited row from its old group,
cleans any orphan, then creates or joins the selected partner's group.

Workout sessions snapshot the effective exercise name at start time:

```js
displayNameOverride || exercise.name
```

Completed workout records preserve that snapped name in `exerciseName`, so
history keeps the name used during the workout even if the routine is renamed
later. Active and completed workout exercise snapshots also preserve
`supersetGroupId` so workout mode can group paired exercises visually without
changing timer behavior.

## In-Workout Exercise Swaps

`src/services/activeWorkoutSwap.js` provides the single deterministic swap
boundary used by manual workout actions and future AI approval flows. A swap
changes only the active workout slot. Before any meaningful reps or weight are
logged, it replaces `exerciseId` and `exerciseName` while preserving prescribed
sets, rep range, rest, logged-set structure, and `supersetGroupId`. It records
the original movement as optional `originalExerciseId` and
`originalExerciseName` fields.

Once a slot contains meaningful logged effort, swapping is rejected with a
clear instruction to clear the sets first. No logged values are destroyed or
reinterpreted. Undo is available for an unlogged swap and removes the optional
original fields. The saved routine is never changed.

## Routine Proposal Contract

`src/services/routineProposal.js` defines the provider-neutral boundary for
future coaching proposals. Version 1 supports `create_routine` and
`modify_routine`; it does not call an AI provider or expose an approval UI.

All proposals identify a target program, and modification proposals also
identify a target routine. Modification operations are an ordered `changes`
array supporting:

- `add_exercise`
- `remove_exercise`
- `replace_exercise`
- `move_exercise`
- `update_exercise`
- `set_superset`
- `clear_superset`
- `rename_routine`

Exercise operations target `routineExerciseId`, never a display name or array
index. Adds include their future stable row ID, while replacements preserve the
target row ID and current superset membership but replace the full exercise
prescription. Moves and insertions use an explicit `afterRoutineExerciseId`;
`null` means the start of the routine.

Create proposals describe an ordered routine directly. Supersets use local
`proposalGroupKey` values on its exercise definitions. Modify proposals use a
`set_superset` operation containing a local group key and stable member row
IDs. Application deterministically translates each valid local key into a
shared `ss-proposal-*` ID, avoids collisions, and removes orphaned groups.

The public boundary is:

```js
validateRoutineProposal(proposal, currentProgram)
// { valid, errors: [{ code, path, message }], normalizedProposal }

applyRoutineProposal(currentProgram, proposal)
// success: { applied: true, errors: [], program, routineId, review }
// failure: { applied: false, errors, program: null, review: null }
```

Validation accepts supplied in-memory program context and performs no reads.
It rejects unsupported versions, unexpected targets, malformed IDs and
prescriptions, missing rows, invalid anchors/grouping, and ambiguous operation
combinations. Application validates first, clones the full program graph, and
returns draft data plus review metadata. It imports no Firebase or storage
services and performs no Firestore, localStorage, workout-history, or active
workout writes. The existing Save Program path remains the only persistence
commit for any future approved draft.

## Program Proposal Contract

`src/services/programProposal.js` is a pure provider-neutral contract for
whole-program candidates. Version 1 supports `create_program` and
`modify_program`. It validates a bounded complete program or coordinated
routine changes before applying anything, then returns a new program graph and
deterministic review metadata. A create appends one program only; a modify
changes only its target program. Invalid routine changes make the entire
proposal fail, so neither path can produce a partial result.

Program proposals reuse `validateRoutineProposal()` and
`applyRoutineProposal()` for the existing operation vocabulary and superset
semantics. The module accepts already-resolved provider exercise IDs and owns
no exercise resolution, AI transport, React state, Firebase, Firestore, or
browser storage dependency. It also does not activate programs, alter planning,
workout history, or active-workout state.

This is a domain foundation only: Rob does not yet generate whole programs,
there is no program-proposal approval UI or creation conversation, and no
whole-program proposal is persisted from this boundary.

The routine builder is search-first and edit-on-demand:

- program management is collapsed into a compact header
- day tabs select the routine being edited
- exercise cards are compact by default
- only one exercise card expands at a time for editing
- custom display names are hidden behind an explicit checkbox
- superset pairing is lightweight and uses a simple partner selection control
- the Add Exercises modal stays open after add-mode selections and resets search for the next addition
- Added state is derived from the selected routine draft, so it remains correct after closing, reopening, or switching routines
- a provider failure keeps the picker open and exposes an explicit Retry action without changing the draft
- swap-mode still closes after the replacement exercise is selected

Duplicate provider exercise IDs are intentionally prevented within one
routine. The same provider exercise remains addable to a different routine.
Every accepted row still has its own `routineExerciseId`, which keeps editing,
reordering, and superset targeting deterministic.

Exercise add, swap, remove, reorder, configuration, and superset changes update
`programDrafts` only. They do not invoke local or cloud persistence directly;
Save Program normalizes and commits the complete draft. Routine creation,
duplication, and archive actions retain their existing structural-action save
behavior.

Regression-prone builder transformations are isolated in
`src/services/routineBuilder.js`. This includes legacy routine normalization,
duplicate-safe adding, swap/remove/reorder, superset cleanup, independent
routine duplication, and workout snapshot creation. Persistence serialization
and the local-first/cloud-fallback boundary are independently testable through
`programData.js` and `programPersistence.js`.

## Exercise Provider

Exercise search is routed through `src/services/exerciseProvider.js`.

The provider exposes:

- `searchExercises(query, filters)`
- `getExerciseById(id)`

- wger API results

Normalized exercise shape:

```js
{
  id,
  name,
  originalName,
  category,
  bodyPart,
  primaryMuscle,
  secondaryMuscles,

  images,
  imageUrl,
```

```js

}
```

search results. The equipment filter is hidden for now because wger equipment
metadata is often incomplete or too generic. Equipment is still displayed on
result cards when available.

The UI uses provider-neutral exercise-library copy. wger attribution belongs in
Settings/About, and image credits appear only inside expanded exercise details
when license metadata exists.

There is no full local exercise taxonomy, local catalog fallback, or local
result set.

## Independent Saved Workout Foundation (066; unactivated)

### Model and offline mapping

The library envelope is `{ version: 1, programs: [], workouts: [] }`:

- Saved workout: `{ id, name, archived, programId: string | null, exercises }`.
  Exercises remain ordered prescriptions with existing `routineExerciseId`,
  stable `exerciseId`, sets, repRange, restSeconds, note, displayNameOverride and
  supersetGroupId. This is a reusable template, never a completed/session record.
- Program: `{ id, name, archived, workoutIds: [...] }` plus retained metadata
  (description, timestamps, existing flags and unknown JSON metadata). No embedded
  `days` or `routines`. Program IDs and workout IDs have separate namespaces.
- Each workout is standalone (`programId: null`, no membership) or belongs to
  exactly one existing program, whose ordered workoutIds lists it exactly once.
  All references resolve; workout, program and per-workout row identities are
  unique in their respective scopes. Empty programs, standalone-only accounts,
  and both lists being empty are valid. Archive status does not change ownership.

`planLegacyWorkoutMigration({ accountId, legacyPrograms })` requires an explicit
account ID; it does not infer one. It returns migrationVersion 1, accountId, ok,
structured code/path errors, a per-account summary, tuple mappings, adjustments
and target. Any failure returns `target: null` with no partial mappings or
adjustments. This is not an executable write plan or authorization to migrate.

Input must be plain JSON (serialize Firestore timestamps explicitly beforehand).
`days` or `routines` is accepted; if both exist they must agree, ignoring object
key order but preserving array order. Conflicting aliases, duplicate program IDs
or duplicate routine IDs within one program fail. Metadata, archived/deleted
flags, empty items, exercise order, identities and all prescription values are
copied, without trimming or defaulting existing values. Missing archive flags
become false; invalid existing flags fail. Program archival never rewrites the
member workout's own archived flag. Legacy deleted flags are retained metadata,
not instructions to delete/filter records.

Globally unique legacy routine IDs are retained as workout IDs. Every occurrence
of a routine ID shared across programs gets
`legacy-workout:<encodeIdentity(programId)>:<encodeIdentity(routineId)>`.
Encoding leaves ASCII letters, digits, dots and hyphens unchanged and replaces
every other Unicode code point (including underscore) with `_lowercaseHex_`.
This is injective and keeps generated IDs in the current executable Rob proposal
ID alphabet; unlike percent escapes it does not introduce rejected characters.
All original IDs are reserved first; a generated collision gets the first unused
`:2`, `:3`, etc. No distinct routines merge. Each mapping records programId,
legacyRoutineId and workoutId. Missing exercise row IDs get deterministic
`legacy-row:<encodeIdentity(workoutId)>:<1-based position>` IDs with the same
collision protection within that workout. A legacy groupId adds an identical
supersetGroupId only if the latter is absent; both conflicting aliases fail.
Additions are individually reported and counted. Existing row IDs, notes, names,
set counts and rest values are never regenerated or rewritten.

The validator follows current prescription bounds (integer sets 1-12, optional

### File, typed representation and actual verification

`nevfit-training-readiness-YYYY-MM-DD.json` is a private, separate format:

```text

          testedDestructiveRestore=false, cutoverAllowed=false
```

`firestoreValueCodec.js` tags every value, including maps/arrays and primitives,
so ordinary user fields cannot masquerade as type markers. It preserves the
SDK-observed Timestamp (seconds/nanoseconds), Bytes, GeoPoint, VectorValue and

NaN, positive/negative infinity and negative zero. References also retain their
project/database identity: SDK DocumentReference.toJSON alone only stores a
relative path. Decode refuses a reference from another database/project rather
than rebinding it. Unsupported types fail closed. This is a codec, not a writer.
The installed SDK's Firestore.toJSON database identity is read for that check;
SDK upgrades must retain/retest this codec contract.

The client cannot recover Firestore integer-vs-double wire distinctions or numeric
precision already lost by SDK decoding. Thus even an exact round trip proves
fidelity to fetched **SDK values**, not to every underlying server wire type.
No file is described as a comprehensive raw server recovery backup.

paths, collection inventory counts and hashes. It serializes the actual package

the fetched source encoding, then recomputes the preflight. No decoder performs
a Firestore write. `verifyTrainingReadinessExport` can perform the same local
checks later; comparison to source data only happens when those source values

## Concrete Firestore Staging Adapter and Proposed Rules (069)

`independentWorkoutStageFirestore.js` implements the 068 adapter contract.
Construction performs no network or database operation. Callers explicitly bind
the current UID, SDK Auth, configured default-database Firestore instance, mounted
account predicate and retained private 067 backup. Other databases or mismatched
UIDs are rejected. No app startup, sign-in, export, deploy, refresh or CI path
constructs/invokes a live adapter. There is no production UI staging action.
The existing developer source dry run remains available and never writes.

Every write method requires `enabled: true` (default false) and exact typed
confirmation `STAGE <signed-in UID>`. SDK auth UID and the mounted account are
checked at entry and after awaited work, including transaction retries. This
gate does not authorize live use: 069 explicitly excludes production staging.
No user's private file, account identifier, training data or hashes were used in
implementation, fixtures, output logs or docs.

### Reads, transactions and verification

`trainingReadinessSource.js` extracts the existing 067 server-only reader without
changing the export format or Settings behaviour. The adapter uses it to fetch
fresh source data, reject cache/pending-write snapshots, validate backup identity
and semantic fingerprints, and reject any active session/preflight error. Target
reads fetch every direct document in both workouts and programsV2, plus the single
`appState/independentWorkoutStage` marker, with no limits or cache fallback.
Missing collections return a confirmed empty inventory; unavailable reads fail.

`claimStage` refreshes sources and uses a Firestore transaction to compare the
exact expected marker before creating the staging lock. A different attempt,
fingerprint, unexpected marker fields/status or a racing marker change fails.
An identical same-attempt staging lock is reused without rewriting it.

`createOrVerifyDocuments` accepts at most 400 unique entries, and only exact
source-derived entries in this account's planned workouts/programsV2 set. Caller
payloads and arbitrary allowed-namespace paths cannot become writes. Legacy
programs, completed history, planning, Rob and other paths are structurally
excluded. After a fresh source check, the transaction reads the lock and all
requested targets before any writes. Existing semantic equals need no write;
differences fail. For absent targets, transaction reads supply existence/version
preconditions, so a racing create causes a retry, then equality/conflict checking.
There is no blind set/merge over an existing target and no delete API.

All marker and target write transactions also read/compare every known relevant
source document from fresh capture, including historical snapshots. Fixed
planning/activeWorkout/exerciseNotes/health paths are checked even when absent,
so a newly created active session or changed known source aborts the transaction.
Native Firestore values are compared through the typed canonical codec. Sources
remain read-only. Transactions that lose a race retry through the same auth,
source, marker and target guards; transaction size/request errors fail closed
and are reported by the existing stage engine, with originals still authoritative.

`completeStage` independently performs a final fresh full source check and exact
target-inventory comparison. Its transaction compares the claimed staging lock,
all expected targets and known sources before writing only the verified marker
with schemaVersion 2, legacyAuthoritative true and cutoverAllowed false. A
server-only marker readback checks the result. The engine also refreshes sources
on a verified-marker reuse before returning success. Interrupted runs retain
matching copies and the lock; same-attempt retries reuse them without repairs.

**Concurrency boundary:** no client holds a global lock across devices. Web SDK
transactions can read known documents, not transactionally enumerate collections.
Known-document changes are guarded through commit; newly inserted documents after
the final collection query cannot be globally excluded. Manual pause on all other
devices is mandatory. The marker records the observed source/target fingerprints,
not a promise that no future or concurrent authorised edit exists. Any later
staging/cutover attempt must compare fresh inventories and fingerprints again.
A stale verified marker is not runtime authority and never initiates cutover.

### Proposed rules and actual security boundary

`firestore.rules` adds only these target matches:

- `users/{userId}/workouts/{workoutId}`: owner-only reads; owner creates require
  matching document ID, non-empty text name, boolean archived status, nullable
  string programId and an exercises list.
- `users/{userId}/programsV2/{programId}`: owner-only reads; owner creates require
  matching ID, non-empty name, boolean archived status and workoutIds list, with
  no embedded days/routines aliases.
- Updates/deletes are denied for both new collections, including for the owner.
  Identical existing targets are skipped by the adapter, not rewritten. These
  staging-only permissions are insufficient for future workout CRUD, which needs
  a separate reviewed rules change. Existing rules are otherwise unchanged.

The one marker remains under the existing owner-only appState rule; no broad
new privilege or backend is added. Rules enforce account isolation, create shape
and immutable target copies, not every nested prescription/membership invariant.
The authenticated owner can still create other shape-valid target documents or
write their marker via other authorised app code under existing rules. Such
inventory conflicts fail adapter verification; a marker alone is not trusted as
permission to cut over. Do not describe owner-scoped rules as preventing all
accidental authorised-owner operations or as a complete server migration lock.

**Rules are committed but NOT deployed by 069.** Current production target access
remains denied. No Firebase rules/functions deployment, live staging, account
cleanup, source rewrite, Training UI or runtime v2 cutover was performed.

### Authority and concurrency

`legacyAuthoritative:true` and `cutoverAllowed:false`. It never selects runtime
storage. Activation creates a separate `appState/trainingModel` with version 2,

the UI does not promise that legacy is still authoritative in that case.

Activation transactions compare the model's absence, verified stage, all planned

absence of the activation marker. Stage/activation source guards include this

when queued; active planned-session saves check their snapshot's version. A
legacy import checks the model before starting and inside every write

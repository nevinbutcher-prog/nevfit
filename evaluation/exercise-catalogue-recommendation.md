# Checkpoint 047 — catalogue strategy recommendation

**Recommendation for independent assessment:** choose **B, a curated Nevfit core keyed to existing WGER IDs with full-catalogue fallback**, beginning with a small reviewed metadata overlay. This is an investigation recommendation, not implementation approval. The audit found real machine eligibility and muscle-granularity gaps, but no production usage data or source comparison proving that a replacement would improve the user experience.

| Criterion | A. Enrich all 907 WGER records | B. Curated core + full fallback | C. Change source/strategy |
| --- | --- | --- | --- |
| First useful effort (engineering estimate) | High: likely several weeks of data review before dependable breadth | Low–medium: approximately **2–4 developer days plus exercise-domain review** for an initial 25–40 ID overlay and offline validation | High: source evaluation, crosswalk, API/search changes, regression and rights review; likely weeks |
| Ongoing maintenance | Reviews all imports and changing names/IDs | Reviews core and explicit exceptions; fallback retains uncertainty | Maintains another source, crosswalk, provider uptime/versioning |
| Coverage | Broadest in principle; incomplete fields still need review | Common verified exercises first; all other WGER IDs remain accessible | Depends on source; no demonstrated Nevfit-specific gain |
| Data reliability/workload | Must correct all conflicts, distinguish direct vs secondary and keep unknowns | Can confidently expose fine groups only for reviewed IDs; unknowns stay unknown | Alternative metadata also needs anatomical validation; field presence alone is insufficient |
| Search and Rob quality | Cleaner full pool eventually, but noisy until coverage is substantial | Core-first ranking/selection could improve common use; fallback/manual choice for unusual cases | Requires a new search/selection integration and relevance assessment |
| Historical IDs | Simple if all current IDs preserved | Simple if core is an overlay, aliases never replace IDs | Requires durable `wger-*` mapping or dual-ID support; many-to-one matching is risky |
| Rights/attribution | Continue WGER attribution and per-entry rights review | Same WGER obligations; curated corrections need source/provenance log | New terms and image rights require separate assessment |
| Scale | 907-field review cost grows with imports | Bounded review effort, ID-keyed lookup scales cheaply; fallback preserves long tail | Operational scale may be feasible but vendor/rights and migration costs grow |

**Why B is the smallest plausible route.** The snapshot has 216 records without equipment, including 45 records whose names match a heuristic machine-pattern check, so full catalogue inclusion cannot be treated as reliable machine eligibility. The taxonomy has 607 low-confidence profiles and merges important muscle groups. A focused overlay can fix reviewed machine access, primary target ambiguity, and search priority for common IDs while leaving unknown records available for manual picking. It should store source values beside reviewed corrections, explicit confidence and reviewer/date/reason, and treat name-based suggestions as review candidates only. The 25-ID [prototype](exercise-curation-prototype.json) demonstrates the schema and uncertainty discipline; it does not validate anatomy or authorize a live overlay. A later user sample (voluntary, privacy-conscious, or aggregate) would be needed to choose the actual first core list. No production usage evidence was available here.

**Proposed smallest next checkpoint, subject to approval:** establish an ID-keyed **reviewed data overlay for approximately 25–40 common exercises**, prioritising machine chest press/fly, lat pulldown/row, leg press, leg extension/curl, calf raise, shoulder raise/press, and conventional free-weight/cable/bodyweight anchors. Require a human exercise-domain review of equipment and primary/secondary muscle evidence, preserve unknown and conflicting fields, and add automated ID/name/source-version and historical-lookup checks. Apply no fractional secondary set credit. Do not add workload charts or recovery models in that step. Whether to activate core-first search or Rob selection should be a separate explicit decision after offline QA demonstrates eligibility and relevance improvements. Estimate **2–4 developer days for overlay/schema/validation**, plus review time that depends on reviewer availability; estimate is not a delivery commitment.

**Alternative source evidence and rights.** [WGER's own README](https://github.com/wger-project/wger/blob/master/README.md) distinguishes application code (AGPL) from exercise/ingredient data (Creative Commons, individual entries), so attribution and per-entry license information should be retained and checked before redistribution or modification. The current Rob snapshot strips those fields; the browser keeps image license/author but not a reviewed per-exercise rights manifest. [Free Exercise DB](https://github.com/yuhonas/free-exercise-db) advertises 800+ entries with equipment and primary/secondary fields under its [Unlicense file](https://github.com/yuhonas/free-exercise-db/blob/main/LICENSE.md); that is a candidate for a **separate** coverage/rights study, not proof of superior muscle data or straightforward image provenance. Its issue tracker includes [unresolved image-rights questions](https://github.com/yuhonas/free-exercise-db/issues/2), so media reuse would need checking. The current [ExerciseDB free API documentation](https://oss.exercisedb.dev/docs) states non-commercial use and attribution requirements; that is a material constraint for a future product. Neither alternative was imported or crosswalked here. License observations are source summaries, not legal clearance. A wholesale source migration is unsupported by this audit.

**Decision gates after any future implementation:** a reviewer verifies each curated ID and variant, equipment, direct/secondary stimulus, and source rights; compare common search queries and generation candidates against a fixed baseline; confirm historical exact-ID lookups and same-name variants; then have users assess whether machine exercises and Rob suggestions are actually more useful. Keep excluded/unknown reasons visible. No production catalogue, prompt, search, Firestore record or workload feature changed in checkpoint 047.

## Codex Implementation Brief — Convert Rob recommendations into validated routine proposals

### Objective

Connect Rob to Fitbot’s existing **provider-neutral `routineProposal` safety boundary**.

Rob may generate **candidate proposal intent**, but Fitbot—not the model—must remain authoritative over:

- program/routine/exercise targeting;
- persistent IDs;
- exercise-provider identities;
- supported proposal version/types/operations;
- prescription validity;
- anchors/order;
- superset grouping;
- conflict detection;
- whether a candidate is considered executable at all.

The core rule for this card is:

```text
Rob suggests
→ Fitbot resolves identities
→ validateRoutineProposal(current in-memory program)
→ only a valid normalized proposal may proceed
```

No generated proposal may mutate program state or persist anything in this card.

The next card will add **human review / approval / application**. Do not implement that early.

---

# 1. Existing architecture to preserve

Fitbot already has the authoritative proposal boundary in:

```text
src/services/routineProposal.js
```

Current constants:

```js
ROUTINE_PROPOSAL_VERSION = 1

ROUTINE_PROPOSAL_TYPES = {
  CREATE: "create_routine",
  MODIFY: "modify_routine"
}
```

Supported modify operations:

```text
add_exercise
remove_exercise
replace_exercise
move_exercise
update_exercise
set_superset
clear_superset
rename_routine
```

Existing validator:

```js
validateRoutineProposal(proposal, currentProgram)
```

returns:

```js
{
  valid,
  errors,
  normalizedProposal
}
```

Existing pure application boundary:

```js
applyRoutineProposal(currentProgram, proposal)
```

already validates first and returns a cloned draft graph.

**Do not call `applyRoutineProposal()` in this card.**

The existing Save Program flow remains the only future persistence commit.

---

# 2. Important architectural distinction

Do not treat raw AI output as a valid `routineProposal`.

Introduce three conceptual stages:

```text
1. Rob candidate
2. Fitbot-resolved proposal
3. Validated routineProposal
```

These are not interchangeable.

### Stage 1 — Rob candidate

Untrusted provider output.

May contain semantic references for exercises that still need resolution.

### Stage 2 — Fitbot-resolved proposal

All required persistent/provider identities have been resolved or generated by Fitbot.

### Stage 3 — Validated proposal

The resolved object has successfully passed:

```js
validateRoutineProposal(resolvedProposal, currentProgram)
```

Only stage 3 may be exposed to later approval/application functionality.

---

# 3. Do not weaken `routineProposal.js`

The existing validator is authoritative.

Do not add AI-specific exceptions such as:

```text
if generatedByRob then allow...
```

Do not bypass:

```js
validateRoutineProposal()
```

Do not silently coerce invalid operations into valid ones.

Do not accept unsupported proposal versions or operations simply because the model emitted them.

If changes to `routineProposal.js` are needed, they must strengthen or generalize the provider-neutral contract—not create a Rob bypass.

Where `context` is deterministic Fitbot coaching/program context and `request` describes what proposal Rob is being asked to produce.


# 7. Scope proposal generation carefully

For:

```text
modify_routine
```

require a valid target:

```text
programId
routineId
```

and send the relevant routine plus enough parent program/profile context to reason safely.

For:

```text
create_routine
```

send the active program and its active routines so Rob can avoid obvious duplication.

Use the current **in-memory draft**, not stale persisted data.

This matches the builder’s existing semantics.

---

# 8. Reuse deterministic Rob context where possible

Do not build a parallel arbitrary program serializer.

Extend or reuse the existing deterministic Rob context model where practical.

Proposal generation needs at least:

```text
program ID
routine IDs
routineExerciseIds
provider exerciseIds
exercise names
ordered prescriptions
superset information
goals
equipment
constraints
```

Stable existing row IDs are especially important because modify operations must target exactly the current draft rows.

---

# 9. Raw AI output should be an envelope

Keep explanatory prose and executable intent clearly separated.

Recommended provider response:

```json
{
  "version": 1,
  "explanation": "The routine has overlapping chest isolation work, so I would simplify it and move lateral raises later.",
  "candidate": {
    "proposalType": "modify_routine",
    "targetProgramId": "program-123",
    "targetRoutineId": "routine-456",
    "title": "Reduce redundancy",
    "summary": "Simplify chest isolation and improve ordering.",
    "changes": []
  }
}
```

`explanation` is user-facing advisory prose.

`candidate` is untrusted machine data.

Never parse prose to derive operations.

Never mix narrative content into executable fields.

---

# 10. Do not let Rob author persistent identities for new entities

Rob may reference existing IDs supplied in context.

It must not be authoritative for newly-created persistent identities.

For existing rows, Rob may return:

```text
targetRoutineExerciseId
afterRoutineExerciseId
memberRoutineExerciseIds
```

but only IDs actually supplied in context.

For new entities:

- new routine ID → Fitbot generates it;
- new routineExerciseId → Fitbot generates it;
- proposal ID → Fitbot generates it if needed;
- superset persistent ID → continue using existing proposalGroupKey/application logic;
- provider-backed exercise ID → resolve through Fitbot’s exercise provider.

Do not trust arbitrary model-generated IDs for those fields.

---

# 11. Existing row targeting rules

For `modify_routine`, all references to existing rows must come from the current in-memory routine.

This includes:

```text
targetRoutineExerciseId
afterRoutineExerciseId
memberRoutineExerciseIds
```

Do not resolve these by:

```text
exercise name
array index
position
fuzzy text
```

The model must return stable `routineExerciseId` values supplied in context.

Unknown IDs must fail.

---

# 12. Safe handling of new exercise suggestions

This is the most important integration detail.

The existing proposal validator requires provider-backed exercise IDs with the existing provider-neutral format.

Rob must not invent a persistent `exerciseId`.

For a proposed new/replacement exercise, use a semantic candidate descriptor before materialization.

For example:

```json
{
  "exerciseRef": {
    "query": "cable lateral raise",
    "name": "Cable Lateral Raise"
  },
  "sets": 3,
  "repRange": "10-15",
  "restSeconds": 90
}
```

This is **candidate data**, not yet a valid `routineProposal` exercise.

---

# 13. Resolve candidate exercise references through `exerciseProvider.js`

Fitbot’s existing exercise boundary is:

```text
src/services/exerciseProvider.js
```

with:

```js
searchExercises(query, filters)
getExerciseById(id)
normalizeExercise(sourceExercise)
```

All new exercise identities proposed by Rob must pass through this boundary.

Do not accept a provider ID merely because the LLM supplied one.

---

# 14. Exercise resolution rules

Implement a resolver such as:

```js
resolveRobProposalCandidate(candidate, currentProgram)
```

which performs provider resolution before validator execution.

For every proposed new exercise:

1. use the semantic search query;
2. call the existing provider-neutral exercise search;
3. determine whether a trustworthy provider-backed result can be resolved;
4. convert it into Fitbot’s provider-backed `exerciseId`;
5. generate any required fresh `routineExerciseId`;
6. only then construct the final proposal object.

If an exercise cannot be safely resolved:

```text
proposal resolution fails
```

Do not guess.

---

# 15. Avoid unsafe “pick first result” behaviour

Do not blindly do:

```js
searchExercises(query)[0]
```

unless the existing search contract provides an unambiguous exact match guarantee.

Prefer deterministic matching based on normalized provider data.

Safe resolution can use:

- exact normalized name match;
- exact known alias match if supported by the existing provider;
- explicit provider-backed identity obtained through provider lookup.

If multiple plausible results remain:

```text
resolution must fail
```

Human exercise disambiguation can be added later if needed.

Do not implement a large new chooser workflow in this card.

---

# 16. Existing exercises may retain known provider IDs

If the candidate is referring to an exercise already present in the program, use the existing exercise’s provider-backed:

```text
exerciseId
```

from current context rather than searching again.

This is useful for operations such as changing prescriptions.

---

# 17. Replace operation semantics

Current validator semantics for:

```text
replace_exercise
```

retain the existing row identity.

Therefore Rob should identify:

```text
targetRoutineExerciseId
```

and Fitbot should resolve only the replacement provider exercise/prescription.

Do not create a new row identity for a replacement if the existing proposal contract preserves the target row.

# 18. Add operation semantics

For:


The candidate may specify:

```text

```

but the anchor must already exist or be valid within ordered proposal semantics.

The existing validator remains authoritative.

# 19. Create-routine identity semantics

Rob may suggest:


Generate IDs using an existing Fitbot ID helper if one already exists.

Do not introduce random incompatible ID formats.

If no shared helper exists, isolate deterministic/unique ID generation in one reusable service rather than embedding it in Rob code.


# 27. Server-side candidate validation

The server should validate the provider output structurally before returning it.

For example:

```js
{
  version: 1,
  explanation: "...",
  candidate: {...}
}
```

Validate:

- correct envelope;
- requested proposal type;
- supported operations;
- required fields;
- bounded strings/lists;
- JSON shape;
- existing reference syntax where applicable.

However:

**this is not the authoritative `routineProposal` validation.**

That occurs only after client-side identity/exercise resolution against the current in-memory program.

---

# 28. Why authoritative validation remains client-side

The current program draft is the authoritative in-memory object and may contain unsaved edits.

Therefore the final call must be:

```js
validateRoutineProposal(resolvedProposal, currentProgramDraft)
```

using the exact current draft used for proposal generation/resolution.

Do not validate only against persisted Firestore state.

Do not fetch a second stale program copy from Firebase for validation.

---

# 29. Guard against draft changing during asynchronous generation

Proposal generation and exercise resolution are asynchronous.

The user could edit the routine while Rob is thinking.

Capture a lightweight deterministic draft identity/fingerprint when generation starts.

Before accepting the final validated proposal:

- confirm the relevant program/routine draft still represents the same source state; or
- rebuild validation against the latest current draft and reject references that are now stale.

Do not silently accept a candidate generated for an older row graph if targets/anchors have since changed.

A simple safe result is:

```text
"This routine changed while Rob was preparing the proposal. Generate it again."
```

Do not persist snapshots solely for this.

---

# 30. Mandatory final validator call

After materialization:

```js
const validation = validateRoutineProposal(
  resolvedProposal,
  currentProgram
);
```

There must be no alternate success path.

Conceptually:

```js
if (!validation.valid) {
  return proposalRejected(validation.errors);
}

return {
  explanation,
  proposal: validation.normalizedProposal
};
```

The object retained for later preview/approval must be:

```text
validation.normalizedProposal
```

not the raw provider payload.

# 45. Anchor semantics

```text

```


# 46. Conflict semantics

Retain current validator behaviour for:

- duplicate row IDs;
- repeated rename;
- conflicting mutation operations;
- multiple grouping operations;
- invalid superset membership;
- operations targeting rows already removed.

Do not preprocess away conflicts before validation merely to make the AI pass.

If the AI generates contradictory operations:

```text

```

and allow explicit regeneration later.

---

Do not introduce a Rob-only duplicate rule.

If changed, add regression coverage for non-AI callers too.

# 64. Retry semantics

Retries must be explicit.

No automatic second paid inference attempt.

A retry should:

1. rebuild/use current in-memory context;
2. regenerate candidate;
3. resolve exercises again;
4. validate against the latest current draft.

Do not retry a stale resolved proposal.

---

# 65. Draft freshness

If the current draft changes after a valid proposal is produced but before later approval:

the proposal must eventually be revalidated before application.

For this card, either:

- clear the transient proposal when relevant draft state changes; or
- mark it stale.

Prefer clearing it for now.

This mirrors the review freshness pattern and keeps the next card simpler.

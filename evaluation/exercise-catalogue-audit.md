# Checkpoint 047 — exercise catalogue audit

**Scope and evidence.** Offline review of the committed `functions/src/rob/robExerciseCatalogue.v2.json` (WGER language ID 2, captured 2026-10-09), its import script, Nevfit search and Rob code, the empty starter program, synthetic fixtures and tests. No production Firestore or personal training history was read. Counts below are snapshot counts, not claims about the current live WGER API or actual user behaviour.

## Reproduce

From the repository root, run `node scripts/auditExerciseCatalogue.mjs`, `node scripts/auditExerciseCatalogue.mjs --selection`, and `node scripts/auditExerciseCatalogue.mjs --prototype`. The script reads committed data only. `--match "machine"` and `--ids wger-73 wger-371` inspect examples. The `--selection` command uses a stated commercial-gym/balanced fixture; it does not sample live generation.

## Existing intelligence and workload suitability

`src/services/rob/robExercisePlanningTaxonomy.js` gives every record a profile. Its primary broad group comes from the source primary string or body part (`source_normalized`, medium), secondary groups come from source secondary fields plus movement/name-based inferred rules, and movement/selection intent/conventionality are mostly name rules. Four ID-and-name-guarded manual exceptions (`73`, `567`, `723`, `507`) correct movement/role or add a broad secondary; they are not a reviewed muscle atlas. Measured taxonomy output: primary known 859/907, unknown 48; secondary `partial` 378, inferred-only 90, unknown 439; movement unknown 434; overall confidence high 4, medium 296, low 607. Selection intent known for 103 records, unknown for 804. These counts describe implementation coverage, not anatomical accuracy.

The broad normalization merges lats/trapezius/back into `back`, all deltoid heads into `shoulders`, biceps/triceps/brachialis/forearms into `arms`, quads/hamstrings/calves into `legs`, and abdominals/obliques/serratus into `core`. Chest and glutes remain distinct. The narrow intent overlay can distinguish name-inferred biceps vs triceps, knee flexion vs extension, and three delt heads for a few isolation entries; it does not change broad primary stimulus or supply reviewed involvement. The active Rob generation/quality heuristic uses another broad name/body-part mapper. Its “working sets by primary muscle” are therefore bookkeeping for broad catalogue labels, not validated muscle workload. Scorecard v2 keeps secondary evidence qualitative and is isolated from active generation; its broad direct-set rollup is also unsuitable for fine-grained workload claims. `planningOverlap` treats any shared broad group as overlap, so distinct biceps/triceps or quad/hamstring exercises can look equivalent. Blueprint fulfilment requires exact broad group/pattern/role (and optional narrow intent), then ranks by conventionality/confidence/setup; it is isolated from the callable. Those components can be reused for ID validation, eligibility, provenance flags, conservative unknown handling, and advisory selection, after reviewed data is supplied. They should not be used as an anatomical truth source or to convert secondary participation into fractional set credit.

## Identity and compatibility

The catalogue keys by `wger-{source.id}`. Browser picker/search and `getExerciseById` use the same prefix; saved routine rows persist `exerciseId` plus their separate `routineExerciseId` through local cache and Firestore program documents. Active-workout rows hold `exerciseId`, name and optional `originalExerciseId`/name after a swap. Completed snapshots copy those fields and logged sets; previous-performance lookup matches exact current `exerciseId`. Rob active generation returns server-authorised catalogue IDs and materializes those IDs into proposals; legacy name resolution selects a provider result ID or asks for a manual choice; workout swaps preserve the replaced ID as traceability. A display-name alias must therefore point to the **same** stable ID, not replace it. A curated core should be an overlay keyed by existing IDs, retain access to the full catalogue and retired IDs for read/historical lookup, and keep display aliases separate from canonical identity. Correcting a mapping changes future interpretation of historical sets: version the mapping and retain provenance/unknowns, but do not rewrite saved workout records. Never collapse same-name IDs without source-level evidence; otherwise previous-performance histories can merge different variants. No migration is recommended or performed.

## Limits

This audit does not verify WGER's present API, individual exercise descriptions, source licenses, machine hardware, instruction quality, anatomical stimulus under varying technique, or real user behaviour. Name-based flags require human review. The prototype is intentionally conservative and does not authorize equipment or quantify secondary set contribution.

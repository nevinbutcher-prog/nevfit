Use the repository's Git integration as the frontend/Vercel deployment path; do not deploy directly to Vercel. Git push authorization is standing and explicit for completed, verified work required by an approved brief. Commit and push to the configured remote and current branch without requesting separate approval. Verify the Git-triggered deployment outcome. This does not authorize force pushes, deleting remote branches, or rewriting shared history. If deployment cannot proceed because the commit has not been pushed or the Git-triggered deployment fails, report exactly what remains rather than describing the deployment as complete.

Firebase deployment authorization is standing and explicit for work required to make an approved brief function in production. After verification, deploy all in-scope Firebase changes needed by the brief, including Cloud Functions, Firestore rules and indexes, Storage rules, and other non-destructive Firebase configuration, without asking for separate deployment approval. Use the Firebase CLI against the repository's configured Firebase project, scope the deployment to the required Firebase resources, and verify the deployed function/rule state. This authorization does not cover deleting production data, removing Firebase resources, changing billing, broad IAM changes, or creating/replacing secret values; those still require explicit user approval. Never describe a Firebase-dependent brief as deployed while its required Firebase resources remain undeployed.

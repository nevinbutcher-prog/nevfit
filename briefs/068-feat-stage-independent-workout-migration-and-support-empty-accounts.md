## Checkpoint outcome B: safe, limited migration implementation

1. Implement a small authenticated **explicitly invoked, non-automatic** staged migration path using 066's pure migration plan and 067's read-only preflight. This is a controlled operation, not a startup migration. **No migration of live data is authorised to run during Codex implementation, testing, deployment or CI.** The user will choose whether to activate it only after independent review and a fresh local backup check.
2. Validate fresh server-only source program documents, account identity, exact expected source identifiers/content fingerprints, full migration-plan invariants, resolved planning/active-session links, and that no target document IDs conflict with existing records. Reject if any active session exists, exports have unresolved preflight errors, source state drifted, writes are pending, or another migration is in progress. Do not rely on a static sample of 6/10/73; reports should reflect live account counts at invocation.
3. Stage independent workout documents in account-scoped `users/{uid}/workouts/{workoutId}` and program representation in a **separate v2 namespace/collection or other explicitly isolated area** (not an in-place overwrite of `users/{uid}/programs/*` because the existing app expects embedded `days`). Use stable deterministic IDs, preserve all relevant template content, and retain the existing legacy programs unchanged. Idempotent retry is required; on partial failure leave legacy data authoritative and report exactly what is staged; do not delete originals or write to completed history.
4. Verify newly staged documents by reading from the server and comparing canonical semantic content, ordering, ownership, counts and stable mappings to the live source and pure plan. Use straightforward batch writes within Firestore limits, or a similarly simple safe staged approach; no elaborate orchestration for a single active account.
5. **Do not cut the live app over to the staged schema in this checkpoint.** Existing program reads/writes, weekly schedule, active workout resume and history remain on the legacy path. Stage an explicit version/verification marker only after successful comparison; markers must never trigger automatic cutover at startup. Existing program edits after staging should make the staging report stale, to be reconciled at a later explicit cutover. Avoid a second persistently dual-writable source of truth.
6. Supply an appropriately guarded, temporary developer/operator-only way to invoke and report staging (e.g. a deliberate action with conspicuous confirmation and exact account identity, separate from ordinary import/export), but do not expose an accidental one-click destructive migration to ordinary new users. If this cannot be done without weakening security rules or broadening scope, implement and test the stage/verify service plus a **dry-run-only** interface/entry point, and flag manual activation as blocked. No Firebase admin secrets, no new privileged backend, no mass migration of test users.
7. Update relevant data contracts and describe later cutover clearly: switching runtime program reads/writes to v2 and saved workout CRUD, preservation of schedule references and completed history, backup v1/v2 compatibility and optional eventual legacy cleanup. **Actual cutover, program deletion, new Workouts library, rename of UI labels and redesign are outside this checkpoint.**
